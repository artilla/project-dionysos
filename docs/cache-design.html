01

합의한 동작

10초

검색 결과는 서버에서 공유

월·지역·인원·박수·시설 유형·대기 포함 조건이 같은 검색은 사용자 ID 없이 같은 결과를 재사용합니다. 전체 검색과 개별 시설 상세도 포함합니다.

직접 조회

최신 업데이트는 항상 원천으로

대상 휴양림의 선택 월·유형과 연박에 필요한 다음 달까지 다시 확인합니다. 완료된 결과로 공통 데이터를 갱신하고 관련 검색 캐시를 무효화합니다.

개인 상태만 분리

개인 검색 응답 캐시는 생략

별도 사용자별 검색 응답 캐시는 두지 않습니다. 계정·쿠키·대기열·작업 진행은 개인 보관하며, 찜과 화면 조건은 브라우저 상태로 유지합니다.

캐시 만료와 저장 데이터 삭제는 다릅니다.

10초가 지나도 기존에 모은 현황은 보존합니다. 결과 내 검색은 저장된 현황을 다시 계산하고, 새 현황 가져오기 또는 최신 업데이트를 실행할 때 원천 조회가 발생합니다.

바뀌는 것은 데이터 격리 경계입니다.

현재는 브라우저(방문자 namespace)마다 본인이 수집한 현황만 열람하고, 열람 자체에 유효한 숲나들e 연결은 필요하지 않습니다. 이 설계는 그 경계를 바꿔, 어느 사용자가 수집한 검색 데이터든 다른 사용자가 같은 조건으로 읽을 수 있게 합니다. 계정·쿠키·대기열·작업 상태의 격리는 그대로입니다. 이 변경으로 바뀌는 기존 테스트는 08절에 정리했습니다.

미결정 정책 · 연결 이력이 없는 방문자의 열람

숲나들e 연결에 한 번도 성공하지 않은 방문자에게 공통 데이터를 보여줄지는 이 문서에서 결정하지 않습니다. 연결 이력을 요구하면 기존 열람 조건에 가깝지만 첫 방문자는 빈 결과를 봅니다. 익명 열람을 허용하면 서비스가 공개 현황 미러가 되므로 요청 속도 제한과 조건 조합 부하(07절)를 함께 정해야 합니다. 두 경우 모두 실제 원천 요청은 수행하는 사용자의 인증과 대기열 절차를 따릅니다.

구현의 임시 기본값은 앞쪽입니다. 숲나들e 연결에 성공한 이력이 있는 방문자(개인 카탈로그를 보유한 namespace)만 공통 데이터를 읽고, 이력이 없는 방문자는 조건 검증만 공통 카탈로그로 수행한 빈 결과를 dataCoverage.state = connect-required로 받고, 화면은 "연결이 필요해요" 안내와 연결 버튼을 보여줍니다(server/app.mjs의 canReadShared, web/app.js의 빈 상태). 미수집·정상 빈 결과 안내와 섞이지 않으며, 정책이 정해지면 서버의 판단 하나만 바꿉니다.

02

세 가지 요청 흐름

A. 결과 내 검색 · 목록과 상세 읽기
검색 조건 선택월 / 지역 / 유형 / 인원 / 박수
→
공통 결과 캐시10초 이내이며 데이터 버전 일치 → 즉시 반환
→
캐시가 없으면 재계산월·지역·유형 범위 묶음에서 조건별 계산 → 결과 캐시 저장

이 경로는 숲나들e를 호출하지 않습니다. 오래된 현황이면 실제 확인 시각과 이전 확인 표시를 유지합니다. 계산에는 공유 소유권을 두지 않고 각 요청이 직접 계산합니다.

B. 전체 또는 조건별 새 현황 가져오기
개인 조회 작업 생성선택 범위를 작은 수집 작업으로 분해
→
공통 원천 캐시 확인같은 원천 요청의 최근 성공 데이터 재사용
→
없거나 만료되면 원천 조회본인 연결과 정상 대기열로 수집 → 저장

전체 범위가 하나의 거대한 캐시가 되지 않도록 지역 목록·정책·시설 목록·날짜 배치 단위로 재사용합니다. 수집은 요청한 사용자의 브라우저가 단계 호출로 진행시키며, 다른 사용자의 수집을 기다리지 않습니다. 배치를 저장할 때마다 공개 쓰기이므로 해당 범위의 버전이 오릅니다.

C. 카드의 최신 업데이트
최신 업데이트 클릭대상 휴양림과 조회 범위를 고정
→
두 캐시 모두 우회이전 캐시나 클릭 전 시작된 수집으로 대체하지 않음
→
성공 결과 공개 반영공통 현황 교체 / 버전 증가 / 화면 즉시 갱신

실시간은 버튼 클릭 이후 실제로 다시 확인한다는 의미입니다. 지속적인 자동 감시·자동 예약은 포함하지 않습니다.

개인 영역

각 사용자의 로그인 정보, 연결 쿠키, CSRF, 대기열 이용권, 작업 ID·진행·실패·재시도는 위 공통 검색 데이터에 섞지 않습니다.

03

저장하는 데이터의 경계

영역내용보관·재사용 정책
공통 원천 캐시지역·휴양림·시설 목록, 예약 정책, 날짜별 공실·대기·휴무 현황같은 원천 요청에 10초. 허용된 필드만 저장하고 원본 HTTP 헤더·쿠키·사용자 정보는 제거합니다.
공통 요금 캐시정규화한 시설 기본요금(개인 할인·최종 결제 금액 제외)기존과 같은 15분. 해당 휴양림의 최신 업데이트가 성공하면 서버 캐시와 브라우저 요금 캐시를 함께 무효화합니다. “기본요금은 하루 안에 거의 변하지 않는다”는 가정은 확인이 필요합니다.
공통 범위 묶음월·지역·유형별로 정규화한 현황 묶음과 그 묶음이 기준으로 삼은 버전버전이 바뀌면 다시 만듭니다. 여러 snapshot 행을 한 번에 읽어 계산에 필요한 필드만 남기므로 행 수·쿼리 수·필드는 줄지만, 묶음을 D1에서 읽고 파싱하는 비용은 남습니다.
공통 검색 결과 캐시조건별 휴양림 목록·입실일·시설 수·시설 상세·공통 확인 범위10초 또는 의존 데이터 변경 중 먼저 도달한 시점까지. 개인 작업 상태와 찜은 포함하지 않습니다.
공통 카탈로그월·지역 목록, catalogRevision, 휴양림 목록을 확보한 지역(knownRegions)로그인 성공 시 받은 카탈로그로 갱신합니다. 조건 검증·기본 월·미조회 지역 계산은 요청자의 개인 카탈로그가 아니라 이 값을 사용합니다.
공통 저장 현황마지막으로 정상 수집한 데이터, 실제 확인 시각, 데이터 버전, 데이터 자체의 완전성캐시 TTL로 삭제하지 않습니다. 만료된 원천 캐시와 구분해 이전 확인 결과로 열람합니다. 지난 월의 보존 기간은 미정입니다(07절).
개인 서버 상태암호화된 계정·인증 세션, 대기열 이용권, 조회 범위·진행·취소·실패 내역기존 브라우저별 저장 공간 유지. 로그인·작업 상태 API는 캐시하지 않습니다. 다른 사용자가 조회하거나 이어받지 못합니다.
개인 브라우저 상태찜·선택 조건·정렬·선택 날짜·열린 상세 화면기존 보관 방식을 유지합니다. 공통 결과 위에 개인 필터를 적용하며 인증 정보를 localStorage로 옮기지 않습니다.
공유 대상은 검색 데이터이며, 계정을 공유하는 기능은 아닙니다.

공통 캐시를 읽더라도 실제 원천 요청은 이를 수행하는 사용자의 인증과 대기열 절차를 따릅니다. 공통 데이터 열람에 연결 이력을 요구할지는 01절의 미결정 정책을 따르며, 캐시 유무가 그 결정을 대신하지 않습니다.

확인 범위

검색 데이터를 공통으로 다루는 것이 이번 설계의 전제입니다. 현재 계산 코드에는 사용자별 예약 자격 입력이 없지만, 원천 응답의 계정 간 동일성은 실측하지 않았습니다. 실제로 계정별 값이 확인되면 해당 필드만 공통 검색 모델에서 분리합니다. 최종 예약 자격·개인 할인 판단을 공통 검색의 보장으로 해석하지 않습니다.

04

캐시 키와 10초의 의미

원천 캐시 키

호출 종류와 실제 데이터 범위를 구분합니다. 지역·휴양림·월·유형·시설 ID 목록·예약 정책 등 응답에 영향을 주는 입력을 빠뜨리지 않습니다.

source:v1:{endpoint}:{canonicalScopeHash}

예: 날짜 배치
휴양림 / 월 / 시설 유형 / 정렬한 시설 ID
조회 구분 / lastDay 등 원천 요청 조건

제외: 사용자 ID, Cookie, CSRF, 대기열 키

기존 날짜 요청은 최대 5개 시설씩 처리합니다. 배치의 ID 순서를 정규화하고, 네트워크에서 막 수신한 데이터의 확인 시각으로 만료를 계산합니다.

검색 결과 캐시 키

동일한 입력은 같은 키가 되도록 기본값·자료형·다중 지역 순서를 정규화합니다. 목록과 상세는 구분하고, 계산 규칙 버전도 포함합니다.

search:v1:{route}:{canonicalQueryHash}

month / 정렬·중복 제거한 regions / type
guests / nights / weekend / includeWait
KST 기준일 / 상세 forestId(해당 시)

유효성(목록): catalog
  + forests:{대상 지역} + range:{월·지역·유형}
유효성(상세): catalog
  + forests:{휴양림의 지역} + snapshot:{월·휴양림·유형}

현재 서버는 지역별 결과를 합칩니다. 1차 적용은 각 지역 API 응답을 공유하며, 다중 지역 통합 API로 바꾸더라도 동일한 정규화 규칙을 사용합니다. 화면에서만 처리하는 이름 검색·찜·정렬·선택 날짜는 현재 서버 키에 추가하지 않습니다.

고정 만료 · 조회 시각 보존

  • expiresAt = createdAt + 10초. 캐시를 읽을 때마다 만료를 연장하지 않습니다.
  • 원천 캐시는 실제 조회 시각을 보존합니다. 다른 캐시나 저장 현황을 읽었다고 새로 확인한 것으로 기록하지 않습니다.
  • 조건별 결과는 여러 시점의 현황을 조합할 수 있습니다. computedAt과 sourceObservedAt을 분리하고, 공통 결과의 확인 시각은 사용한 현황 중 가장 오래된 시각을 기준으로 합니다.
  • 원천 캐시 10초와 결과 캐시 10초를 이어 붙여 실시간 확인 기간으로 안내하지 않습니다. “최근 원천 확인”을 표시하는 응답은 의존 원천 데이터의 유효 시각도 넘지 않아야 합니다.
  • 현재 15분 기준의 ‘이전 확인’ 표시는 원천 데이터의 나이 표시입니다. 새 10초 캐시 TTL과 별개의 개념으로 유지합니다.
  • 배치가 긴 전체 조회는 전체 데이터가 한 시점에 확인된 결과가 아닙니다. 배치별 확인 시각을 보존하며, 전 범위를 “방금 확인”으로 표시하지 않습니다.

버전이 오르는 시점 · 키마다 다릅니다

버전 키는 무효화 범위와 같습니다. 어떤 공개 쓰기가 실제로 무엇을 바꿨는지에 따라 그 키만 오르며, 바뀐 것이 없으면 오르지 않습니다.

  • catalog · 로그인으로 받은 월·지역 목록의 내용이 달라졌을 때만. 지역 목록·정책 공개는 이 키를 건드리지 않으므로 다른 지역의 캐시가 함께 무효화되지 않습니다.
  • forests:{지역} · 그 지역 휴양림 레코드(이름·유형)가 실제로 바뀌었거나 지역 목록을 처음 확보했을 때. 같은 내용의 재공개는 올리지 않습니다.
  • range:{월·지역·유형}, snapshot:{월·휴양림·유형} · 그 범위의 현황이 실제로 쓰였을 때. 일반 수집의 날짜 배치 저장(server/app.mjs의 saveSnapshot)도 공개 쓰기이므로 배치마다 오르고, 관측 시각 규칙(07절)으로 건너뛴 쓰기는 올리지 않습니다.
  • forest:{휴양림} · 최신 업데이트의 세대 번호. 최신 업데이트 공개에서만 오르며, 일반 수집은 건드리지 않습니다.
  • price:{휴양림} · 최신 업데이트 성공 시. 요금 캐시와 브라우저 요금 캐시가 이 값으로 무효화됩니다.

결과적으로 어떤 범위가 수집 중일 때 그 범위의 목록·상세 캐시는 배치마다 재계산되어 10초 캐시가 사실상 우회됩니다. 수집 중인 사용자 본인이 배치 즉시 반영을 보는 동작을 유지하기 위해 이를 감수하며, 다른 지역·다른 휴양림의 캐시는 그대로 유지됩니다. 버전을 개인 작업 시각이나 작업 ID로 만들지 않습니다(05절).

2단 캐시 · 줄이는 비용과 남는 비용

1차는 월·지역·유형별 범위 묶음입니다. 여러 snapshot 행을 한 번에 읽어 계산에 필요한 필드만 남기고 그 시점의 버전을 기록합니다. 2차는 조건별 검색 결과이며, 묶음과 같은 버전일 때만 유효합니다.

  • 범위 묶음이 줄이는 것은 행 수·쿼리 수·불필요한 필드입니다. 조건이 다른 요청도 같은 묶음을 읽으므로 인원·박수·주말·대기 조합이 많아도 D1 읽기는 한 종류로 모입니다.
  • 묶음도 D1에서 읽고 JSON으로 파싱하는 한 파싱 비용은 남습니다. 파싱된 객체를 요청 간에 재사용하는 것은 Workers isolate 메모리에 의존하므로 보장하지 않으며, 설계의 전제로 삼지 않습니다.
  • 계산 시간과 절감 폭은 실측 전에는 수치를 제시하지 않습니다.

같은 조건을 다시 검색하는 예

0초 · 사용자 A

10월 / 경기·강원 / 숙소 / 4명 / 2박 검색. 저장 현황을 계산해 공통 결과 캐시 생성.

3초 · 사용자 B

같은 조건 검색. 공통 결과 재사용. B의 찜과 개인 진행 상태는 별도 표시.

6초 · A가 갱신

특정 휴양림 최신 업데이트 시작. 실제 조회가 진행되는 동안 기존 성공 결과 유지.

갱신 성공 시

공통 데이터 버전 변경. 10초가 남아 있어도 관련 조건 캐시는 다음 요청에서 재계산.

예시는 동작 설명이며 성능 측정치가 아닙니다. 다른 사용자의 열린 화면은 다음 조회 때 반영하며, 실시간 푸시 기능은 추가하지 않습니다.

05

최신 업데이트의 완료 조건

  1. 클릭한 범위를 고정합니다.

    해당 휴양림·월·숙박 유형과 연박에 필요한 다음 달 범위를 작업에 저장합니다. 실행 중 사용자가 검색 조건을 바꿔도 원래 작업 범위는 유지합니다.

  2. 새로운 원천 조회를 시작합니다.

    서버 내부 fresh 모드로 정책·시설·날짜 캐시를 모두 우회합니다. 클릭 전에 시작된 일반 조회나 이전 성공 캐시로 완료 처리하지 않습니다. 기존 개인 연결 잠금과 정상 대기열 처리를 유지합니다.

  3. 임시 결과를 검증합니다.

    필요한 월·유형·시설·날짜가 모두 확인될 때까지 기존 카드 결과를 유지합니다. 일부 실패는 개인 작업 상태로 알리고 공통 정상 결과를 실패 데이터로 바꾸지 않습니다.

  4. 성공 결과와 데이터 버전을 함께 공개합니다.

    대상의 전체 월·유형을 하나의 D1 batch로 반영합니다. 작업이 읽었던 세대 번호를 조건으로 하는 버전 갱신을 같은 batch에 넣어, 조건이 맞지 않으면 데이터도 버전도 바뀌지 않습니다. 월·지역·유형 버전과 해당 휴양림 버전을 함께 증가시켜 목록·달력·상세가 서로 다른 세대를 읽지 않게 합니다.

  5. 관련 캐시를 무효화하고 즉시 다시 표시합니다.

    이 범위를 참조하는 조건별 결과 캐시와 범위 묶음은 버전 불일치로 사용하지 않습니다. 갱신한 원천 응답으로 공통 원천 캐시를 교체합니다. 해당 휴양림의 공통 요금 캐시(15분)를 무효화하고, 브라우저의 요금 캐시(web/prices.js)도 같은 휴양림 범위로 비워 화면 가격을 새로 조회합니다.

  6. 사용자의 화면 맥락을 유지합니다.

    현재 조건·선택 날짜·스크롤·찜과 카드 순서를 유지합니다. 다른 사용자는 다음 검색에서 새 현황을 활용합니다. 관련 캐시 무효화가 다른 휴양림의 원천 재조회를 뜻하지는 않습니다.

버전은 개인 작업 시각으로 만들지 않습니다.

현재의 queryVersion = job.updatedAt 대신 공통 데이터 버전을 사용합니다. 목록은 catalog·대상 지역의 forests:·range: 버전을, 상세는 catalog·해당 지역의 forests:·해당 휴양림의 snapshot: 버전을 비교합니다(04절). 범위 버전은 최신 업데이트뿐 아니라 일반 수집의 배치 공개에서도 오르고, 세대 번호(forest:)는 최신 업데이트에서만 오릅니다. 같은 월·유형의 다른 검색 캐시도 일부 재계산될 수 있지만, 다른 휴양림을 다시 수집하지는 않습니다.

계산할 현황과 버전을 같은 읽기 시점에서 가져오고, 계산 중 버전이 바뀌면 예전 결과를 새 버전 캐시에 넣지 않습니다. 다중 지역 결과도 지역별 버전·확인 시각을 유지해 한 지역의 갱신이 전체 지역을 최신으로 보이게 하지 않습니다.

캐시 정책은 HTTP 메서드만으로 결정하지 않고 기능별 허용 목록으로 적용합니다. 개인 상태가 섞인 현재 응답 전체를 공유 캐시에 넣지 않습니다.

캐시 응답의 경계

공통 payload · 캐시 대상
  query, forests, dataCoverage,
  dataVersion, sourceObservedAt

응답 메타데이터 · 비캐시
  servedAt, cacheAge, cacheHit

개인 구역 personal · 비캐시, 같은 응답
  job, forests[id].failed / inProgress

개인 상태 API · GET /api/job, /api/session*
  jobId, progress, failures, connected

개인 구역을 별도 API로 나누면 갱신마다 요청이 두 배(다중 지역이면 N+1)가 되므로 같은 응답 안에 비캐시 구역으로 둡니다. API 응답의 Cache-Control: private, no-store는 유지할 수 있습니다. 서버 내부 D1 캐시와 브라우저·CDN HTTP 캐시는 별개입니다. 사용자 응답의 Set-Cookie나 인증 실패 응답을 공유하지 않습니다.

현재 저장 현황은 그대로 보존합니다.

기존 개인 snapshot을 삭제하거나 일괄 공개로 전환하지 않습니다. 개인 현황으로의 fallback은 저장소 전체가 아니라 snapshotKey(월·휴양림·유형) 단위로 판단합니다. 공통 저장 현황에 해당 키가 없을 때만 요청자의 개인 현황을 그 키에 채우고, 새 정상 수집부터 정규화한 공통 데이터로 바꿉니다. 일반적인 캐시 누락마다 개인 과거 값으로 되돌아가지는 않습니다.

dataCoverage.state는 shared(공통 데이터), incomplete(미조회 범위 있음), empty(확인했으나 시설 없음), personal-fallback(공통 데이터가 없는 키를 개인 현황으로 채움), connect-required(연결 이력이 없어 공통 열람을 보류), unavailable(카탈로그 없음)을 구분합니다. fallback을 포함한 응답과 connect-required 응답은 공통 결과 캐시에 기록하지 않습니다. 연결을 해제했거나 계정을 삭제한 브라우저는 개인 카탈로그가 남아 있어 계속 shared로 읽습니다.

개인 행이 남아 있어도 공통 결과 캐시는 사용합니다. 적중한 payload가 개인 휴양림을 모두 포함하고, 조건에 필요한 개인 snapshot 키를 scopePublications로 모두 덮으면 그 적중을 그대로 반환합니다. 조건에 필요하지 않은 개인 행(예: 숙소만 있는 휴양림의 야영장 현황)은 fallback을 강제하지 않습니다.

07

동시 요청과 실패 처리

동일 요청이 몰릴 때 · 수집은 브라우저가 진행

수집은 요청한 사용자의 브라우저가 /api/job/step을 호출할 때만 한 단계씩 진행되고, 서버가 스스로 이어가지 않습니다. 따라서 공통 키에 수집·계산 소유권을 두고 다른 사용자를 기다리게 하지 않습니다. 기다리게 하면 상대의 탭이 닫히거나 멈춘 동안 함께 멈춥니다.

  • 원천 조회는 공통 원천 캐시에 있으면 생략하고, 없으면 각자 본인 연결과 대기열로 조회합니다. 같은 지역을 나란히 수집하는 두 일반 수집은 서로 충돌하지 않으며, 한 걸음 뒤따르는 쪽은 앞선 쪽의 원천 응답을 재사용합니다.
  • 결과 계산은 공유 소유권 없이 각 요청이 수행합니다. 같은 버전의 계산 결과는 어느 요청이 먼저 저장해도 같습니다.
  • 사용자별 기존 원천 연결 잠금은 유지합니다. 공유하는 것은 성공 데이터이며 쿠키·대기열 이용권이 아닙니다.
  • 캐시 적중이어도 버전·접근 확인을 위한 DB 읽기와 HTTP 요청 자체는 남습니다.

늦은 결과의 덮어쓰기 방지 · 두 가지 공개 규칙

공개 쓰기는 하나의 D1 batch 안에서 조건을 확인하고 반영합니다. 조건이 맞지 않으면 데이터도 버전도 바뀌지 않습니다. 세대 확인과 공개 반영을 분리하지 않습니다. 확인만 먼저 하고 나중에 쓰는 방식은 늦은 쓰기를 막지 못합니다.

  • 최신 업데이트 · 세대 비교(CAS). 작업 시작 시 읽은 forest: 세대 번호가 그대로일 때만 전체 월·유형을 함께 공개하고 세대를 올립니다. 세대는 최신 업데이트끼리만 다투며, 밀린 작업은 원천 캐시를 우회해 다시 조회합니다.
  • 일반 수집 · 관측 시각 규칙. 세대를 비교하지 않고 snapshotKey 단위로, 저장된 관측 시각보다 오래된 현황은 쓰지 않습니다. 완전한 현황은 부분 현황을 대체할 수 있습니다. 그래서 오래된 일반 수집이 최신 업데이트보다 늦게 끝나도 최신 결과를 덮어쓰지 못하고, 일반 수집끼리는 충돌하지 않습니다.
  • 건너뛴 범위는 그 작업에서 superseded로 마무리합니다. 남은 원천 요청을 하지 않고, 개인 구역의 staleByJob도 표시하지 않습니다(공통 데이터가 더 새롭기 때문).
  • 명시적 갱신은 이전 일반 수집을 최신 결과로 재사용하지 않습니다. 동일 요청의 재전송은 같은 request ID로 중복 실행을 방지합니다(08절).
  • 사용자가 resume·retry를 누르면 충돌 재시도 횟수는 초기화하되 세대 기준은 유지해, 보관해 둔 범위가 더 새로운 갱신을 덮어쓰지 않게 합니다.

조회 실패 또는 일부 누락

인증 실패·네트워크 오류·대기열 실패·파싱 실패를 정상 공통 캐시로 저장하지 않습니다. 완전한 빈 목록은 유효할 수 있지만, 누락이나 실패를 ‘예약 가능 없음’으로 바꾸지 않습니다.

  • 개별 최신 업데이트가 실패하면 직전 성공 결과 유지.
  • 전체 수집은 완료한 범위부터 공개하고 데이터 완전성을 표시.
  • 실패 사유와 재연결·재시도 상태는 해당 사용자에게만 표시.

캐시 만료 또는 저장 오류

만료된 조건 캐시는 공통 저장 현황에서 재계산합니다. 원천 캐시는 현황 수집 요청이 있을 때만 다시 채웁니다. 캐시 쓰기만 실패한 경우 계산·조회한 성공 응답은 반환할 수 있습니다.

  • 권위 있는 현황·버전 저장까지 실패하면 업데이트 완료로 표시하지 않음.
  • 이전 결과를 반환할 때 실제 확인 시각과 실패 상태 유지.
  • 만료 항목은 접근 시 정리하고 정리량을 제한. 개인 저장 현황에는 TTL 삭제를 적용하지 않음.
  • 공통 저장 현황의 지난 월 보존 기간과 정리 규칙은 미정. 구현 전에 결정하며, 결정 전까지는 삭제하지 않음.

조건 조합이 많을 때

결과 캐시 키는 인원(1–100)·박수·주말·대기·지역·유형의 조합이므로, 조합이 바뀔 때마다 결과 캐시는 미스가 되고 재계산이 일어납니다. 지금은 요청자가 자기 현황만 읽어 자기 응답만 느려지지만, 공통 저장소에서는 조합을 바꾸는 요청으로 전 지역 재계산을 반복시킬 수 있습니다.

  • 조건과 무관한 읽기는 1차 범위 묶음으로 공유합니다(04절). 조합이 달라도 D1 읽기는 묶음 한 종류로 모이고, 남는 것은 조건별 계산입니다.
  • 요청 속도 제한 또는 계산 상한은 익명 열람 허용 여부(01절)와 함께 결정합니다. 익명 열람을 허용한다면 제한 없이 배포하지 않습니다.
  • 계산 시간은 실측 후에만 근거로 사용합니다.

기대 효과와 한계

동일 조건 재검색의 DB 행 읽기·집계를 줄이고, 여러 사용자의 근접한 원천 요청도 재사용할 수 있습니다. 범위 묶음은 행 수·쿼리 수·필드를 줄이지만 묶음을 읽고 파싱하는 비용은 남습니다. 첫 전체 조회나 서로 겹치지 않는 요청은 줄지 않고, 수집이 진행 중인 범위에서는 배치마다 버전이 올라 10초 재사용이 거의 일어나지 않습니다. 효과는 캐시 적중률·실제 원천 호출 수·응답 시간으로 판단하며, 이 문서에는 실측 절감률이나 계산 시간을 제시하지 않습니다.

근거와 확인 범위

  • 현재 저장·조회 구조

    server/app.mjs, server/store.mjs, server/worker.mjs, server/domain.mjs 및 web/regions.js를 기준으로 작성했습니다. 소스 기준 커밋은 9f3a5d5이며, 공통 캐시 구현은 그 위의 작업 트리(미커밋)에 있습니다. 실제 D1 마이그레이션 적용·배포는 아직 하지 않았습니다.

  • Cloudflare Workers · Cache API

    Cache API 내용은 데이터센터 밖으로 자동 복제되지 않습니다. 이 설계는 현재 프로젝트에 연결된 D1을 공통 데이터와 버전의 기준 저장소로 사용하고, CDN 캐시를 필수 구성으로 추가하지 않습니다.

  • Cloudflare D1 · Read replication

    읽기 복제본을 도입한다면 Sessions/bookmark를 활용해 갱신 이후의 읽기 일관성을 유지해야 합니다. 이 문서는 복제본 설정 변경을 포함하지 않습니다.

  • 숲나들e · 월별현황조회

    원천 조회는 기존 공식 화면의 정상 로그인·대기열·조회 절차를 따릅니다. 검색 현황은 예약 확정이나 개인 자격 확인을 대신하지 않습니다. 수집 결과를 대기열을 거치지 않은 다른 사용자에게 보여주는 것은 이 절차 설명이 다루지 않는 새 동작이며, 01절의 미결정 정책과 함께 판단합니다.

  • 검토 반영 · 1차(2026.09.09)

    소스 대조 검토에서 합의한 내용을 반영했습니다. 01절 데이터 격리 경계와 미결정 열람 정책, 02·07절 브라우저가 진행시키는 수집 모델과 공유 소유권 제거, 03·04절 범위 묶음(2단 캐시)·버전 증가 시점·공통 카탈로그·유효성 기준 통일, 05·06절 세대 조건부 D1 batch 공개·요금 15분 유지와 브라우저 요금 캐시 무효화·snapshotKey 단위 fallback·같은 응답의 비캐시 개인 구역, 07절 조건 조합 부하, 08절 연결 표 보완과 영향받는 테스트입니다.

  • 검토 반영 · 2차(2026.09.09) · 구현 검토 후 수정

    구현을 이 문서와 대조해 세 결함을 재현하고 고쳤습니다. 같은 지역의 일반 수집 두 건이 세대 충돌로 서로를 재시작시키다 실패하던 문제는 일반 수집을 관측 시각 규칙으로, 최신 업데이트만 세대 비교로 분리해 해결했습니다(07절). 지역 목록·정책 공개마다 카탈로그 버전이 올라 전국 캐시가 무효화되던 문제는 버전 키를 catalog·forests:{지역}·range:·snapshot:·forest:·price:로 나누고 내용이 바뀔 때만 올리도록 고쳤습니다(04절). 개인 행이 남은 방문자가 공통 결과 캐시를 영구히 우회하던 문제는 적중 payload가 필요한 개인 키를 모두 덮으면 적중을 사용하도록 고쳤습니다(06절). retry·resume은 충돌 재시도 횟수를 초기화합니다. 회귀 테스트 7개를 tests/shared-regression.test.mjs에 추가했고, 수정 전 코드에서는 7개 모두 실패, 수정 후에는 전체 107개 중 106개가 통과합니다(남은 1개는 pricing.test.mjs의 ko-KR 날짜 포맷 단언으로, 검증 환경의 ICU 차이입니다).

  • 보완 · 미연결 방문자 안내(2026.09.09)

    연결 이력이 없어 공통 열람을 보류한 응답을 connect-required로 구분하고, 화면은 "숲나들e 연결이 필요해요" 안내와 연결 버튼을 보여줍니다. 연결 후 미수집(incomplete), 정상 빈 결과(empty), 연결 해제·계정 삭제 후 저장 결과 열람(shared)은 그대로이며, 서버·UI 회귀 테스트로 네 상태를 각각 고정했습니다. 임시 열람 정책 자체는 바꾸지 않았습니다.

  • 남은 확인 사항

    공통 저장 현황의 지난 월 보존 정책은 미정입니다. 범위 묶음을 배치마다 재생성하는 쓰기 비용과 D1 batch 문 수(지역 목록 공개 1회에 약 80문) 제한은 실측·확인이 필요합니다. 마이그레이션은 배포 전에 적용해야 하며(worker는 스키마를 만들지 않음) 적용 경로가 저장소에 정의돼 있지 않습니다. server/local.mjs의 문서 허용 목록에는 기존 두 문서만 있어 이 문서는 로컬 서버로 열리지 않습니다.

이번 산출물은 설계 문서와 그 구현 1차입니다.

2차 반영에서 바뀐 코드는 server/shared.mjs, server/app.mjs와 신규 tests/shared-regression.test.mjs이고, 미연결 방문자 안내 보완은 server/app.mjs, web/app.js와 테스트 세 파일입니다. DB 적용·커밋·배포는 하지 않았습니다. 실제 계정 간 응답 비교와 캐시 성능 측정은 수행하지 않았습니다. 기존 아키텍처·구현 계획의 과거 상태 표시와 이번 설계안을 혼동하지 않도록 문서를 별도로 작성했습니다.
